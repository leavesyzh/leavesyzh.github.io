高层概览

随着用于训练模型的 GPU 集群规模不断增大，出现了如数据并行、张量并行、流水线并行、上下文并行，以及 ZeRO 或核融合等技术，以确保 GPU 始终保持高利用率，从而显著缩短训练时间并最大化昂贵硬件的使用效率。更进一步地，随着对大模型的微调在实际应用中越来越受重视，人们发现微调在特定领域数据上能带来更好的效果，这通常也需要相同的分布式训练技术。作者在书中依次介绍了这些技术的原理和特点。

本书所涉及的全部技术方案，均旨在应对以下三项深层挑战，这三者构成大规模语言模型训练中的核心制约因素：

  1. 显存占用（Memory Usage）：显存容量是训练的硬性边界条件。一旦某一训练步骤的内存开销超出显卡容量，训练过程将无法继续。因此，优化显存使用是一切并行策略和模型设计的前提。
  2. 计算效率（Compute Efficiency）：最大化计算资源的利用率至关重要。理想情况下，GPU 应始终处于计算状态，而非因等待数据加载、通信延迟或同步阻塞而空闲。本书重点介绍如何通过流水线调度、重叠计算与通信等机制来提升计算吞吐。
  3. 通信开销（Communication Overhead）：大规模分布式训练中，不同 GPU 之间的数据交换是主要瓶颈之一。通信一旦阻塞，将直接导致算力浪费。为此，需尽可能减少通信量，优化通信路径，优先使用节点内高速链路，并通过异步/并行机制与计算过程重叠，从而降低等待成本。

这三大挑战之间通常存在张力，优化一方往往需牺牲另一方。例如，激活重计算可降低显存消耗，但会增加计算量；张量并行有助于减小单卡内存压力，但引入更多通信开销。因此，在显存、计算与通信三者之间做出合理取舍，是实现训练任务高效可扩展的关键。

单卡训练

模型训练流程

在单卡 GPU 上训练模型通常包括三步：

  1. 前向传播（Forward Pass）：将输入数据送入模型，从第一层依次传递到最后一层，计算出模型输出（如分类结果或预测值）。在此过程中，模型会记录中间的激活值，用于后续反向传播阶段；

    显存占用来源主要有：

    • 模型权重（Parameters）：需要加载到显存中供前向使用，常驻显存；
    • 激活值（Activations）：每一层的中间输出（activation）必须暂时保存在显存中，用于后续反向传播中求导；
    • 临时张量（临时计算中间变量）：如矩阵乘法中产生的临时结果，也会短暂占用显存。

    🔸 显存高峰之一：激活值是前向过程中主要的显存开销，尤其在深层模型中尤为显著。

  2. 反向传播（Backward Pass）：基于前向输出与真实标签之间的损失，利用链式法则（链式求导）从输出层反向计算每一层的梯度。这些梯度反映了损失对每个参数的影响，是参数更新的依据；

    显存占用进一步增加，原因如下：

    • 梯度张量（Gradients）：每个参数都需要保存一个梯度，与权重大小相同，占显存；
    • 额外的中间变量：链式法则中的梯度传播需要计算图中一些临时张量和缓存信息；
    • 前向保存的激活值也仍然需要保留直到反向结束。

    🔸 显存高峰之二：此阶段激活值、梯度、临时变量同时存在，显存压力最大。

  3. 优化步骤（Optimizer Step）：使用优化器（如 SGD、Adam 等）根据计算得到的梯度更新模型参数，从而使损失函数趋于最小。更新后模型进入下一个训练迭代周期。

    虽然相比前两步显存需求较小，但也有一些固定开销：

    • 优化器状态（如 Adam 的一阶动量和二阶动量）：通常为每个参数额外保存 2 个变量，显存占用是参数大小的 2 倍；
    • 参数和梯度仍需常驻：直到 optimizer 更新完成。

    ✅ 相对较轻：优化器步骤本身对显存压力不大，但优化器状态是累计开销。

为什么激活值是显存瓶颈而不是权重？

  • 模型权重虽然大，但只存一份（常驻），不会随着 batch 或层数而增长；
  • 激活值随着网络深度、batch size、token 长度成比例放大；
  • 且每层都要保存，不能提前释放，导致累积占用暴涨。

Batch Size

**批大小（batch size）**是模型训练中非常重要的超参数，会同时影响模型收敛和吞吐量。小 batch size 有利于训练初期快速更新权重，且梯度带有随机性。但在训练后期，小 batch size 可能使梯度噪声过大，模型无法收敛到最优的点。而相反，如果 batch size 太大，虽然可以让梯度估计更精确，但会使每次更新投入的计算代价增大，从而降低整体效率。

有些大模型在训练时会采用动态调整的 batch size。例如，在 DeepSeek-V3/R1 的训练过程中，在前 469B token 的训练中，batch size 会从 3072 输入序列逐渐增加到 15360，随后保持 15360 不变。

batch size 同时也影响训练相同数据集所需的训练时间：较小的 batch size 会导致需要更多次的优化步骤（Optimizer Steps），而优化步骤通常是最耗算力的。因此小 batch size 往往会拉长整体训练时间。但是在实际训练中，batch size 的最终性能对其附近的一些取值并没有那么敏感，通常存在一个相对平缓的区间。

在 LLM 预训练社区中，batch size 通常会用 token 而不是样本量来表示（bst = Batch Size Tokens），这样就不必关心具体输入序列长度，用 tokens 来衡量可以更直观地比较训练代价。在最简单的单机训练场景下，bs（以样本计）和 bst（以 token 计）可以通过序列长度（seq）相互转化：

Transformer 的显存占用

训练时的显存占用

在训练神经网络模型时，GPU 显存通常由以下几部分组成：

  1. 模型权重（Weights）

    • 模型的可训练参数，常驻显存。

    • 通常每个参数占用 2~4 字节（如 FP16 / FP32）。

    • 示例：一个 1B 参数的模型（FP32）约占用 4 GB 显存。

  2. 模型梯度（Gradients）

    • 每次反向传播后，为每个参数保存对应梯度。

    • 大小与模型参数一致。

    • 示例：1B 参数模型的梯度（FP32）约为 4 GB。

  3. 优化器状态（Optimizer States）

    • 如使用 Adam 优化器，需为每个参数维护两个额外状态（momentum 和 variance）。

    • 通常大小是权重的 2×。

    • 示例：1B 参数模型，Adam 优化器状态约为 8 GB（FP32）。

  4. 激活值（Activations）

    • 前向传播中每一层输出都要保存，以便反向传播计算梯度。

    • 占用通常为模型参数的 2× ~ 6×，依赖于 batch size、序列长度、模型深度等。

    • 示例：深层 Transformer 模型激活值可能占用 20~30 GB。

  5. 临时缓冲 / CUDA kernel / Fragmentation

    • CUDA 内核本身运行会占用一定显存（一般约 1~2 GB）。

    • 还包括中间张量计算、缓存、layernorm/softmax 临时数据等。

    • 显存碎片也会导致部分空间无法有效使用。

这些需要存储的数据以张量形式存在，不同张量有不同的 形状（shape） 和精度（precision）。形状由例如 batch size、序列长度、模型隐层维度、注意力头数、词表大小，以及是否进行模型切分等超参数决定；精度则对应 FP32、BF16 或 FP8 等格式，会影响每个元素所占的字节数（4、2 或 1 字节）。

在训练过程中，显存占用并不是静态的，而是一个包含多个阶段的流程，每个阶段对显存的需求不同。

  1. 前向传播阶段（Forward Pass）
      • 输入数据依次通过每一层计算，每层的激活值（intermediate activations）需要保存用于后续反向传播。
      • 显存占用随着网络的“深入”逐步增加，直到最后一层。
      • 通常此阶段的显存主要由：
        • 激活值（activations）
        • 中间计算缓存（如临时的矩阵乘法 buffer）

    • 🔺 显存使用逐层递增，达到一个峰值。

  2. 反向传播阶段（Backward Pass）
      • 使用前向时保存的激活值，依次向后计算梯度。
      • 每个权重的梯度值开始在显存中出现。
      • 有些中间张量可以被释放，因此：
        • 部分显存被释放
        • 部分新的显存被分配（梯度）

    • ⚖️ 显存波动，有释放有增长，整体可能接近峰值。

  3. 优化器更新阶段（Optimizer Step）
      • 优化器（如 Adam）使用梯度计算新的参数值。
      • 此时：
        • 模型权重被更新
        • Adam 优化器会维护两个额外的状态变量（如一阶/二阶动量）
      • 优化器状态也会占用一部分常驻显存。

    • ⚠️ 此阶段新分配的优化器状态会进一步增加显存占用，但不释放。

  4. 释放阶段 / 下一轮开始前
    • 本轮 forward/backward 中产生的激活值、中间缓存被释放。
    • 但权重、梯度、优化器状态仍常驻显存。

混合精度

对于这些参数以及对应的梯度，在显存中需要的空间就是参数个数乘以每个参数的字节数。在传统的 32 位浮点（FP32）训练中，权重和梯度都是 4 字节，优化器在使用 Adam 时，需要存储动量和方差各 4 字节，还会加上一些管理用的结构。总结起来：
$$
m_{params}=4N
\
m_{grad}=4N
\
m_{opt}=(4+4)*N
$$

出于稳定性考虑（参见下文的混合精度训练部分），通常不会采用完全的低精度训练，而是使用一种高低精度混合的方法，称为混合精度。如今混合精度训练的默认设置通常是大部分计算采用 BF16（每个参数和梯度需要 2 个字节），同时保留一份 FP32 格式的模型权重和梯度副本，因此每个参数总共需要 12 个字节。除了参数和梯度之外，我们还需要存储优化器的状态：以 Adam 优化器为例，这需要存储动量和方差，为了数值稳定性，这两项通常以 FP32 格式存储，各占 4 个字节，因此占用的字节数为：
$$
m_{params}=2N
\
m_{grad}=2N
\
m_{params_fp32}=4N
\
m_{opt}=(4+4)N
$$
混合精度本身并不会减少总体显存需求，因为虽然参数本身变少了，但又**多了一份 FP32 副本，甚至如果把梯度也保存在 FP32，整体开销还会上涨。但它能带来很大好处：用 BF16 进行前向/反向计算可用到 GPU 的低精度优化运算单元，速度更快，同时前向传播中激活所需的显存也能减少，这在大 batch 或长序列时尤为重要。因为激活值占用在训练中可能比权重还高，尤其是长序列、深层模型、大 batch 情况下；混合精度训练允许 activations 用 BF16 表示，可以极大减少训练时峰值显存；这也意味着我们可以用更大的 batch size、序列长度，或者更复杂模型，而不会 OOM（Out of Memory）；

激活重计算

激活重计算（Activation Recomputation），也称为 Gradient Checkpointing 或 Rematerialization，是一种常用的显存优化技术，核心思想是：在前向传播过程中有选择性地丢弃部分中间激活值，等到反向传播需要时，再通过重新执行部分前向计算来还原这些激活值。这种方法通过牺牲一定的计算冗余，换取显存的大幅节省，特别适用于大模型训练过程中显存成为瓶颈的场景。

在默认的训练模式下，深度模型会在每一层（如 Attention、MLP、LayerNorm 等）之间保留完整的激活值，以便在反向传播时直接使用。然而，这种做法在面对长序列输入、大 batch size 或超大模型时，会导致激活值占用的显存远超模型权重和优化器状态，成为主要的显存瓶颈。

开启激活重计算后，训练框架只会在部分关键节点（称为 checkpoint）保留激活值，其余中间激活则在 forward 阶段计算后立即释放。反向传播阶段，若需要某个已被丢弃的激活值，模型会从最近的 checkpoint 开始重新执行一段前向子图以恢复它。这一机制显著降低了峰值显存开销，使得原本无法训练的深层模型在现有硬件资源下得以运行。

激活重计算的典型开销是增加约 20%～30% 的前向计算量，但在计算能力相对富余、显存资源紧张的环境下，这一权衡是非常值得的。许多现代训练框架（如 PyTorch、DeepSpeed、Megatron-LM、HuggingFace Transformers）均原生支持该机制，并提供灵活的 API 控制 checkpoint 的粒度与策略。

在实际实施中常见有几种策略来决定哪些激活值需要保存：

  • Full 重计算：该策略在每个 Transformer 层之间仅保留层的输入与输出激活值，而将层内的所有中间激活（例如 Attention 模块中的 Q/K/V、MLP 中的中间表示）全部舍弃。在反向传播阶段，需要对每一层执行完整的前向过程以重新计算这些激活，因此被称为 “Full”。它能够带来最大程度的显存节省，尤其适合极大模型和长序列训练场景。但其代价是较大的计算开销，通常会增加 30% 至 40% 的训练计算量，对整体训练速度影响显著。
  • Selective 重计算：相较于 Full，更为精细化。该策略基于对不同模块激活值大小和重算成本的分析，选择只对特定层或模块执行重计算。根据原始 recomputation 论文的研究，注意力模块的激活值（如 attention score、context vector）通常远大于 MLP 模块，而其重算所需的计算量却更小。因此，Selective 重计算会优先选择对 Attention 部分进行重算，而保留 MLP 等模块的中间激活，以实现更优的“显存-计算”平衡。例如在 GPT-3（175B）模型的实验中，Selective 策略在仅增加约 2.7% 的计算量的前提下，就实现了约 70% 的激活显存节省，展现了极高的效率。

梯度累加

**梯度累加（Gradient Accumulation）**也可以用于避免因过大的 batch size 导致的显存爆炸,常用于解决因过大的 batch size 而导致显存溢出（OOM）的问题。其核心思想是：将原本一次性处理的大 batch，拆分为多个更小的 micro-batch，分别进行前向和反向传播并累加梯度，最后再统一进行一次优化器更新（optimizer step）。这样可以在不降低全局 batch size 的前提下，显著减少每次前向传播过程中激活值所需的显存。

具体流程如下：

  1. 将原始的 global batch size（gbs） 切分为若干个 micro batch（mbs）；
  2. 每次迭代中，依次对每个 micro-batch 执行 forward 和 backward；
  3. 梯度会在多个 micro-batch 之间进行累加（通常是未归一化的和）；
  4. 累加完成后（即处理完一个 global batch），执行一次 optimizer.step() 更新参数，并清空梯度。

这种方式避免了同时加载整个大 batch 所需的庞大激活图，从而有效控制显存峰值。梯度累加并不会影响训练精度或收敛性，只是在时间维度上将一次大 batch 的训练拆分为多次小批次累积完成。

需要注意的是，梯度累加虽然可以缓解大 batch 带来的激活显存压力，但它本身也引入了一些新的资源开销。在启用梯度累积时，训练框架必须为每个参数保留一个缓冲区用于跨多个 micro-batch 累加梯度。这意味着这些梯度缓冲在整个累积周期内（即多个 forward-backward 之间）都必须常驻内存，无法像非累积模式那样在每次反向传播后立即释放，从而增加了参数/梯度层面的显存占用。

此外，梯度累积还要求在每一个优化步骤之前，顺序地执行多次前向和反向传播，直到完成完整的 global batch 计算。这种做法虽然显存友好，但也会显著增加每个训练 step 的总计算时间，进而减慢整体训练速度，特别是在显卡算力充足但显存受限的场景下，这种“以时间换空间”的策略就显得尤为明显。

因此，梯度累加本质上是一种显存和训练吞吐率之间的权衡机制。它在显存有限时非常实用，尤其是在长序列、大模型或单卡训练等场景下，但在高吞吐率是关键目标的分布式训练中，可能并不是最优选择。

数据并行（Data Parallelism）

数据并行（DP）的核心思想是：在多块 GPU 上复制相同的模型参数副本，每张卡独立处理一部分 mini-batch（即 micro-batch），完成前向和反向传播，每次 iteration 结束后，各卡的梯度通过 All-Reduce 聚合并同步，以保持模型一致性。

  • DP 是从空间维度解决问题：通过横向扩展，将同一个模型副本部署到多张 GPU 上，按数据维度切分 batch，并行计算和同步梯度，从而提升整体训练吞吐能力。
  • GA 是从时间维度解决问题：通过纵向拆分，将一个大 batch 分成多个更小的 micro-batch，按顺序依次完成前向和反向传播，延迟执行优化器更新，以换取每一步更小的显存消耗。

因此，DP 更关注 跨设备的并行性和速度提升，而 GA 则用于 在单设备上平衡显存负载。两者结合使用，就能在空间上扩展模型规模，同时在时间上压缩每步计算所需资源，是大规模模型训练中极为常见且互补的组合方案。

在每个 GPU 使用不同的微批次意味着每个 GPU 上会有不同的梯度，为了保持各 GPU 上模型实例的同步，模型实例之间的梯度将在反向传播过程中、优化步骤之前，通过一种称为all-reduce的操作进行平均。

All-Reduce 聚合

All-Reduce 是一种高效的跨多设备梯度聚合和同步操作，确保数据并行训练中所有设备的模型梯度一致，实现同步更新。

  • Reduce 操作：把每个设备上的数据按某种规则（如求和、最大值、最小值等）合并到一起，生成一个汇总结果。
  • All-Reduce 是在 Reduce 的基础上，不仅计算汇总结果，还把该结果广播回所有设备。换句话说，All-Reduce 会把各个设备上的数据进行合并，然后让每个设备都获得这个合并后的统一结果。

在数据并行训练中，每个 GPU 计算自己的梯度副本，为了让所有 GPU 的模型参数保持一致，需要将所有 GPU 上计算的梯度求和（或平均）。All-Reduce 就完成了这一步骤：它把各个 GPU 的梯度向量做元素级求和，然后把求和后的梯度结果同步回所有 GPU，这样每块 GPU 都拥有相同的、更新好的梯度，可以用来更新模型参数。

假设有 4 块 GPU，分别计算的梯度张量是：

  • GPU0: [1, 2, 3]
  • GPU1: [4, 5, 6]
  • GPU2: [7, 8, 9]
  • GPU3: [10, 11, 12]

All-Reduce (求和) 的结果，即所有 GPU 都得到相同的张量 [1+4+7+10, 2+5+8+11, 3+6+9+12] = [22, 26, 30]。

一个简单的数据并行实现通常会在反向传播全部完成后，统一触发一次 all-reduce 操作，将所有梯度同步到各个 GPU。但这种计算与通信串行执行的方式效率极低，因为在通信过程中，GPU 资源会处于闲置状态，导致计算资源浪费。更优的做法是尽可能实现通信与计算的重叠，使梯度同步与反向传播计算并行进行，从而最大化硬件利用率，提高训练效率。

优化一：在反向传播过程中实现梯度同步的重叠

通过将梯度同步（ All-Reduce）与反向传播计算并行执行，可以显著提高训练效率。具体做法是在每层或每组层计算完对应梯度后，立即启动该梯度的同步通信，而不是等全部反向传播完成后再统一同步。这样，通信过程与后续层的梯度计算同时进行，最大限度减少 GPU 空闲时间，提升整体训练吞吐量。

计算与通信的重叠减少了整个模型中等待梯度同步所花费的时间。梯度同步（至少部分地）可以与反向传播并行进行，从而显著加速数据并行。

优化二：对梯度进行 bucket 化

GPU 在处理大张量时通常能发挥更高的计算和通信效率。如果对每个参数单独执行 All-Reduce，会产生大量的小规模通信操作，导致通信效率低下。更优的策略是将多个梯度合并到一个较大的“bucket”中，统一进行一次 All-Reduce，这样可以显著减少通信次数和开销，从而提升整体训练效率。

进行通信操作时，张量必须在内存中是连续的才能避免额外的拷贝。因此常常会预先分配与激活值或参数大小相同的连续内存块，专门用于通信。不过这样会带来额外的峰值内存占用。

优化三：与梯度累加结合

在显存受限或希望使用更大有效批量（effective batch size）时，可以结合梯度累加技术。具体做法是在多个微批次（micro-batches）内累积梯度，而不是每个微批次都立即进行梯度同步。只有在累积完预定数量的微批次后，才启动一次 All-Reduce 操作同步梯度。这样既减少了通信频率，又能够在显存限制下模拟更大批量训练，有效提升训练稳定性和效率。

数据并行的问题

虽然数据并行能够很好地将 All-Reduce 梯度同步与反向计算重叠以节省时间，但当规模增大时，这一优势开始显现不足。当 GPU 数量扩展到数百甚至上千时，节点之间的通信协调成本显著上升，网络带宽需求迅速膨胀，反而抵消了数据并行带来的计算加速效果。此时，随着每增加一张 GPU，系统的整体计算效率可能不升反降，出现**规模不经济（diminishing returns）**现象。

在数据并行（Data Parallel, DP）设置中，虽然最初随着 GPU 数量的增加，训练吞吐量能显著提升，但当 GPU 数超过某个临界点后，吞吐量增长趋缓甚至下降。这主要由于：

  • 通信开销急剧上升：DP 依赖于 All-Reduce 在每轮迭代同步所有梯度，GPU 越多，同步越慢，尤其跨节点通信成为瓶颈；
  • 全模型复制的内存开销不变：DP 会在每张 GPU 上完整复制一份模型参数，因此每卡所需的显存不会随着 GPU 数的增加而减少；
  • 并行效率下降：通信和调度开销抵消了计算并行带来的加速，导致边际收益递减甚至变负。

另一方面，DP 还有一个关键限制：

每张 GPU 至少要能容纳一个 micro-batch（即 MBS ≥ 1）。

原因在于：

  • 前向和反向传播需要实际的输入数据，如果一张卡上连一个样本都放不下，计算无法进行；
  • 这是 DP 的基本假设 —— 每卡独立计算自己的前后向，然后同步梯度。

这在训练大型模型（如 LLaMA-2 70B 或 GPT-3 175B）时成为瓶颈：即使采用激活重计算（activation checkpointing）等节省显存的技术，也可能无法将整个模型和 MBS=1 的数据同时加载到一张 GPU 上。

零冗余优化器

数据并行可以提高吞吐量，但也带来了额外的内存浪费：所有 DP 副本都要存储同样的优化器状态、梯度和参数，这些对象在 DP 副本之间完全重复，占据了大量显存。为了解决这个问题，ZeRO（Zero Redundancy Optimizer） 提出了一种划分式并行方案，通过在数据并行维度对参数、梯度和优化器状态进行切分（sharding），从根本上减少冗余显存开销。虽然 ZeRO 的分片策略会引入一些额外的通信操作（用于在需要时重建完整张量），但其带来的显存节省远远大于通信代价，特别是在大模型场景下。

ZeRO 按照分片粒度的不同，分为三种优化阶段：

ZeRO-3 优化器状态 + 梯度 + 参数（Parameters） 最彻底节省，显存需求除以 N（也叫 FSDP）

虽然梯度张量被切分了，但 ZeRO-2 的通信机制并没有引入新的原语：

  • 仍然使用 Reduce-Scatter 进行梯度同步（不同于 DP 的 All-Reduce）；
  • 在参数更新后，通过 All-Gather 恢复完整参数，用于前向传播；
  • 所有通信仍然可以与计算阶段进行重叠，以隐藏延迟。

相比 ZeRO-1，ZeRO-2 通常是最佳选择，因为：

  1. 更低显存占用：在 ZeRO-1 的基础上进一步切分梯度，节省额外 的内存；
  2. 无额外通信开销：与 ZeRO-1 使用完全相同的通信操作（Reduce-Scatter + All-Gather）；
  3. 部署成本低：实现上仅需对 ZeRO-1 做小幅改动；
  4. 在大多数训练规模下都是更优选择：尤其适合超大模型（如数十/百亿参数）训练。

ZeRO-3：添加参数分区

在 ZeRO-1 和 ZeRO-2 的基础上，ZeRO-3（也称 Fully Sharded Data Parallel, FSDP） 进一步将 模型参数本身 也进行切分，彻底解决了单卡无法容纳完整参数的问题。

为了在前向和反向传播中进行计算，每一层的参数都需要临时重建完整权重。因此，ZeRO-3 比 ZeRO-2 多出以下通信操作：

  • 前向传播中：每一层开始前执行一次 All-Gather，将该层的参数从所有节点收集回来；
  • 反向传播中：由于前向后立即释放了参数，反向传播开始前还需再执行一次 All-Gather；
  • 反向传播后：梯度同步仍通过 Reduce-Scatter 完成（与 ZeRO-2 相同）。

张量并行（Tensor Parallelism）

在大模型训练中，ZeRO 可以将参数、梯度和优化器状态进行分片，大幅减少显存占用。然而，ZeRO 并不能切分 激活值（Activations），导致随着模型深度、序列长度、batch size 增加，激活显存成为瓶颈。为了解决这个问题，引入了更底层的并行方式 —— 张量并行（Tensor Parallelism, TP）。

张量并行可以分片权重、梯度、优化器状态、分片激活值，并且在计算前不需要先聚合完整张量。张量并行利用了矩阵乘法的分布式性质。在张量并行中，张量将沿着特定的维度分成 N 个分片，并分布到 N 个 GPU 上。矩阵可以在列部分或行部分进行分片，从而产生行并行和列并行。以如下两种等价形式为例：

  • 列分片（Column Linear）

    即：B 的列被切分到不同 GPU，每张卡只负责计算自己的那一列

  • 行分片（Row Linear）

    即：A 的行被切分，最终只需聚合结果即可（无需预先汇总 A 或 B）

假设输入 X 是一个 (bs, 4096) 的激活，权重 W 是一个 (4096, 8192) 的线性层权重，如果使用 4-way 张量并行：

GPU 权重 W 切分 激活 X 切分 输出切分（列）
0 W[:, :2048] X 全量 X @ W_0
1 W[:, 2048:4096] X 全量 X @ W_1
2 W[:, 4096:6144] X 全量 X @ W_2
3 W[:, 6144:8192] X 全量 X @ W_3

最终通过 All-Gather 拼接输出，得到完整 (bs, 8192) 的结果。

Transformer 中的张量并行

Transformer 模型主要由两个核心模块构成：

  • 多头注意力（Multi-Head Attention，MHA）
  • 前馈神经网络（Multi-Layer Perceptron，MLP）

Tensor 并行（Tensor Parallelism, TP）能够将上述模块的计算与内存分布到多个 GPU 上，从而扩展模型规模并降低单卡显存压力。

前馈神经网络的张量并行通常采用以下结构：

  1. 列并行：第一层线性（FC1）层的输出矩阵按列切分；
  2. 行并行：第二层线性（FC2）层的输入矩阵按行切分。

这种顺序比从行并行开始然后是列并行更高效，因为中间结果无需 All-Reduce 聚合，可跳过一次通信。在实际训练中，输入通常已在多个 TP 等级之间同步，无需重复广播。

对于多头注意力的 Q/K/V 和输出矩阵，可以按以下方式分片：

  • Q/K/V：按列切分，即每个 GPU 负责不同注意力头或其子集；
  • 输出投影矩阵：按行切分，最终通过 All-Reduce 合并输出。

这种分法也适用于多查询注意力（MQA）或分组查询注意力（GQA）结构。

值得注意的是，tensor 并行度不应超过 Q/K/V 头的数量，因为每个 TP 实例需要保持完整的头部（否则无法在每个 GPU 上独立计算注意力，并且需要额外的通信操作）。在使用 GQA 时，TP 度实际上应小于 K/V 头的数量。例如，LLaMA-3 8B 具有 8 个键/值头，因此 tensor 并行度应优先不超过 8。如果为此模型使用 TP=16，则需要在每个 GPU 上复制 K/V 头并确保它们保持同步。

张量并行通过分片减少显存使用，但也引入通信原语：

  • 前馈层与注意力层输出需执行 All-Reduce 聚合；
  • 该通信操作无法完全与计算重叠，会显式暴露在前向传播路径上；
  • 在每层结束前，必须同步全部中间输出才能继续下一步计算。

在 Transformer 的每个解码器层的前向传播过程中，Tensor 并行度（TP）引入了一个显式的同步点：模型需要在各个 TP 等级之间执行一次 All-Reduce 操作，用于聚合各张卡上分片计算的中间结果。这个 All-Reduce 是不可避免的，它的作用是将所有分片的输出汇总成完整的张量，以便进行后续的 LayerNorm、残差连接等操作。因此，该同步操作无法与前向传播的其他计算步骤完全重叠，形成了通信瓶颈，增加了前向传播的关键路径长度。随着并行度的增加，每张 GPU 的计算吞吐量会逐渐下降。这种性能下降的主要原因在于：更高的并行度会引入更多的跨设备通信，尤其在跨节点场景下表现尤为明显。

在实际应用中，当 Tensor 并行度从 8 扩展到 16 时，计算效率已有显著下降；继续扩展至 32，通信开销进一步放大，导致性能下降更加剧烈。其根本原因在于，Tensor 并行所依赖的 All-Reduce、All-Gather 等操作在跨节点间需通过较慢的网络通信链路完成，而不能完全隐藏在计算路径后。在单节点内部，GPU 间可以通过高速互联（如 NVLink）进行通信，带宽更高、延迟更低，通信成本相对可控。但一旦涉及多节点，网络瓶颈成为主要限制因素。

尽管如此，提升 Tensor 并行度的一个显著好处是可以显著降低每张卡上的内存压力，使得训练更大规模模型或使用更大批次成为可能。因此，这一策略体现了分布式训练中的典型权衡关系：计算效率与内存可用性之间的平衡选择。

序列并行（Sequence Parallelism）

上下文并行（Context Parallelism）

在使用 张量并行与 序列并行 的训练设置中，模型的参数（如权重）和中间激活值被切分并分布在多个 GPU 上，从而显著减轻了单个 GPU 的显存压力。然而，当训练序列长度不断增加（例如扩展至 128K tokens 甚至更长），依然可能面临内存瓶颈，原因如下：

  1. TP 级别处理的是完整序列
    虽然模型参数在多个 GPU 之间分片，但每个 GPU 仍需处理整段输入序列。因此，激活值在序列维度上并未被切分，仍需完整保留。这在长上下文输入下会导致激活占用随序列长度线性增加，最终超出设备内存上限。
  2. 激活重计算策略的局限
    虽然可以通过激活重计算（Activation Checkpointing）减少中间激活的存储开销，但该策略：
    • 仍需保留部分层间边界的激活值，用于构建反向传播链；
    • 无法减少这些保留激活的长度维度，随着序列加长，这部分内存占用仍然不断上升；

上下文并行的目标是在 长序列训练场景中进一步降低单卡显存压力，其本质是将序列并行的思路扩展到整个模型，与张量并行协同工作，在 序列维度 和 张量维度 上同时进行切分。

  • 沿序列长度切分输入数据，即将一个长序列划分为若干子段（sequence chunks），每个 GPU 负责处理其中一部分；
  • 对整个模型进行序列维度切分，而非仅局部模块（如 TP + SP 中的部分线性层）；
  • 大多数模块（如 MLP、LayerNorm）是逐 token 操作的，因而天然支持此种切分，且不会引入跨设备通信；
  • 类似数据并行的方式，在反向传播后进行一次 All-Reduce 操作来同步梯度，确保权重更新一致。

由于这种切分方式对输入进行划分、而非模型权重，通信量通常较小，计算与通信重叠也更容易调度，因而总体效率较高。

但注意力模块（Self-Attention）存在跨 token 的信息依赖：

  • 每个 token 的 Query 需要访问序列中其他 token 的 Key/Value 信息；
  • 在因果注意力中，至少需要访问当前位置之前的所有 token；
  • 如果序列被多个 GPU 拆分处理，则会造成 Key/Value 数据横跨设备，此时就必须进行跨 GPU 的通信。

环形注意力

在上下文并行中，为了支持跨 GPU 的注意力计算，必须交换各个序列切片的 Key/Value（KV）信息。若直接进行全量通信，代价极高。因此，一种更高效的方案是采用 环形注意力（Ring Attention）。

假设有 4 个 GPU，输入序列被沿序列长度维度切分为 4 个段，每个 GPU 仅持有一个 token 的 Q/K/V。整个注意力计算过程分为若干个时间步，按照如下步骤执行：

  1. 初始时每个 GPU 仅有自己的 K/V 分片；
  2. 每一轮，每个 GPU 向下一个 GPU 发送一段自己的 K/V（非阻塞），同时从上一个 GPU 接收另一段；
  3. 在等待接收的同时，它对当前已有的 K/V 执行部分注意力计算；
  4. 如此往复 N 轮（其中 N 是 GPU 数），直到处理完所有 token 的注意力；
  5. 最终，Attention 的结果等价于 All-Gather 的输出，但内存和带宽压力被分散。

每个 GPU 持续完成这些步骤，直到收集完所有其他序列位置的 KV 并完成整个注意力计算。这种逐步通信与计算重叠的方式减少了峰值内存需求，并提升了带宽利用率。由于数据在 GPU 之间按环形路径传输，因此被称为 Ring Attention。

但是在因果注意力中，每个 token 只能看到它之前的 token。因此在注意力得分计算 中：

  • Softmax 按行计算；
  • 每行所需的 K/V 来自该 token 的所有前序 token；
  • 当序列在多个 GPU 间按顺序切分时，靠前的 GPU 可以立刻计算，而靠后的 GPU 则必须等待前面所有 GPU 的 K/V。

假设有 4 个 GPU，每个 GPU 拥有 4 个 token：

  • GPU1 拥有 token 1-4；
  • GPU2 拥有 token 5-8；
  • GPU3 拥有 token 9-12；
  • GPU4 拥有 token 13-16。

在计算 token 13 的注意力时（位于 GPU4），它需要访问 token 1-12 的 K/V，即 GPU1、2、3 的数据。因此 GPU4 在计算前必须等待多轮通信，造成 等待时间长、工作负载重；而 GPU1 则几乎立即完成，处于空闲状态。

之字形环形注意力

为缓解上述负载不均问题，可采用 之字形分布（Zig-Zag Partitioning），即：

  • 不按顺序将 token 分配给 GPU；
  • 每个 GPU 同时拥有早期和晚期 token；
  • 这样可使注意力掩码中每个 GPU 计算任务更均衡。

虽然通信需求增加（因为每个 GPU 需要来自所有其他 GPU 的 KV），但计算负载得到显著平衡，提升整体吞吐。

通信模式的两种实现方式

为支持上下文并行中的 KV 数据交换，常见的通信方式有两种：

  1. All-Gather 实现

    • 所有 GPU 同时收集其他 GPU 的全部 KV；
    • 通信在单步完成，结构简单；
    • 临时内存占用高（需存储完整 KV）；
    • 适用于通信更快、内存相对富余的场景。

  2. All-to-All（环形）实现

    • KV 按块在 GPU 间环形传输；
    • 每次通信的数据量小，通信步骤被分散；
    • 通信与计算高度重叠，降低内存压力；
    • 结构更复杂，但在内存受限时更具优势。

流水线并行（Pipeline Parallelism）

当训练长序列时，序列并行与上下文并行可以有效缓解单个 GPU 的激活内存压力。但如果内存瓶颈的根源在于模型本身的规模过大（如参数量达到 70B+），这些方法就显得作用有限。即使采用这类技术，单节点内的 4–8 块 GPU 也难以容纳完整模型的权重。为此，可以引入第四种并行策略：流水线并行（Pipeline Parallelism）。

流水线并行通过将模型的不同层划分到多个 GPU 上，使每张卡仅负责部分层的计算，从而显著减少每卡所需存储的参数量。例如，在使用 8 个 GPU 的场景下，可将模型划分为 8 个阶段，每张卡负责连续的几层。

尽管权重被成功划分，激活值仍需在各个 GPU 间传递。前向传播时，每张卡会接收上一个阶段传来的激活并继续处理；反向传播时，同样的激活也要传递回来参与梯度计算。由于每个阶段都需要处理完整 batch 的激活，每张卡的激活内存并未得到本质削减。

在 流水线并行（Pipeline Parallelism） 中，跨设备传递的激活张量指的是上一个阶段（stage）输出的那一层的激活值，即 当前阶段所需的输入激活张量，而不是整个模型所有层的激活值。虽然跨设备传输的只是某一层的输出，但：

  • 每个 stage 在自身负责的层内，仍然会产生多个中间层激活值；
  • 这些中间激活值需要在反向传播中使用，要么保存、要么重算；
  • 并且这些激活是对 整个micro-batch 做计算产生的，张量规模大（例如 [batch_size, seq_len, hidden_size]）。

流水线并行引入了新的通信模式：按顺序传递激活张量。这不同于数据并行中通过 All-Reduce 同步梯度，或 ZeRO 并行中同步参数的方式。在这种机制中，每张 GPU 都是前一张 GPU 的下游，等待其输出作为自己的输入，串联成一个计算流水线。流水线并行尽管原理简单，但高效实现较为复杂，必须要考虑以下问题：

  • 激活传递延迟：后续阶段必须等待前面阶段输出完成，存在依赖阻塞
  • 低 GPU 利用率风险：若仅使用大 batch 逐一传递，会造成资源闲置
  • 通信与计算重叠难度较高：不易像张量并行那样进行充分的通信隐藏

为什么 1F1B 能节省显存？

  • 在 AFAB 中，所有前向执行完后，才开始反向，因此需存储所有 m 个微批的激活；
  • 在 1F1B 中，一旦微批 i 完成前向并移交至下一层，当前层即可立刻进行其反向传播；
  • 所以只需保留前 p 个微批的激活（也即当前流水阶段中正在等待反向的激活），内存使用为 O(p)。

交错执行

一种优化方法是在保持流水推进的同时，交错前向传播与反向传播，只要某个微批次完成了前向传播，就尽早触发它的反向传播，这样就能及时释放已不再需要的激活值。

交错执行（Interleaved Execution）用于同时解决气泡浪费和激活内存膨胀这两个主要瓶颈。它通过交替执行前向传播（Forward）和反向传播（Backward），在保持流水推进效率的同时，显著降低内存开销。

在标准流水线中，所有微批次（microbatch）通常会先全部执行前向传播，然后再执行反向传播。这会导致：

  • 激活值必须为所有微批次长期缓存，直到反向传播；
  • 显存使用迅速上升，尤其当微批次数 mmm 增大以减少流水线气泡时。

交错执行的解决方式是：一旦某个微批次完成了前向传播，立刻启动其反向传播，无需等待全部前向结束。这实现了两个目标：

  1. 前/反向并行执行 —— 有效填满流水线，缩小气泡；
  2. 及时释放激活值 —— 释放内存，避免爆炸性增长。

不过，交错流水线也带来了额外的通信代价。由于模型在同一设备上被分为多个阶段，每一轮计算中需要多次在 GPU 之间传递激活值和梯度。这使得通信量以 倍的速度增长，调度也更加复杂。因此，虽然交错方式在理论上能提高计算并行性，减少气泡，并节省激活内存，但它同时也放大了通信开销，特别是在跨节点通信时。这种设计的实际效果，取决于硬件带宽、模型结构以及并行度参数等因素。实际工程中往往需要在计算效率、通信开销和内存节省之间进行精细权衡。

专家并行（Expert Parallelism）

近年来，专家混合模型受到了越来越多的关注，例如 GPT-4、Mixtral，以及最近的 DeepSeek-V3/R1。这类模型的基本思想是，每一层不是单独使用一个前馈模块（feedforward module），而是可以并行使用多个模块，并通过不同的路径处理 token。

MoE 层的设计使其能够在专家（expert）维度上轻松实现并行计算，即专家并行（Expert Parallelism, EP）。由于前馈层完全独立，可以将每个专家的前馈层放置在不同的计算节点上。相比于张量并行 TP，EP 更加轻量级，因为它不需要拆分矩阵乘法，只需要将 token 的隐藏状态正确路由到相应的专家即可。

在实际应用中，EP 通常会与其他并行方式结合使用，例如数据并行 DP。这是因为 EP 仅影响 MoE 层，并不会像上下文并行 CP 那样在序列长度维度上对 token 进行分片。如果仅使用 EP，GPU 仍然会对所有非 MoE 模块执行冗余计算。通过将 EP 与 DP 结合，可以有效地在 GPU 之间分片专家模块和输入批次，如下图所示：

找到最佳训练配置

前面已经讨论了用于训练大型模型的多种并行技术，包括数据并行（DP）、张量并行（TP）、流水线并行（PP）、上下文并行（CP）等。接下来的问题是：实际训练时应如何选择并组合这些技术？这个问题没有固定答案，需要结合模型规模、GPU资源、集群拓扑等因素，通过实验调优找到最适合的组合。以下是一个推荐的决策流程：

步骤 1：将模型加载到内存中

首先，确保完整的模型副本可以在某种配置下适配到当前硬件资源中。通常有两种情况：

  1. GPU资源充足

    • 小于10B参数：
      • 单节点使用 TP 或 ZeRO-3 即可满足需求。
    • 10B~100B模型，需使用多个GPU，可选择：
      • TP + PP（张量+流水线并行）
      • TP + ZeRO-3（张量+数据并行）
      • 单独使用 ZeRO-3
    • 512+ GPU规模：
      • 纯 ZeRO-3 通信开销较大，推荐使用 TP + PP + ZeRO-2 的组合。
    • 1024+ GPU规模：
      • 通常使用 TP（如 TP=8）+ ZeRO-2 + PP 的三重并行结构。
    • 特殊情况：
      • 长序列任务：引入上下文并行（CP）
      • MoE模型：使用专家并行（EP）

  2. GPU资源紧张

  • 启用激活重计算（recompute）以减少显存需求。
  • 增加梯度累积步数，以在较小显存下模拟大批次训练。

步骤 2：实现目标全局批次大小

步骤1中只关注了如何加载模型，但实际训练中还需达到合理的全局批次大小（GBS）。

  • 若当前批次过小：
    • 增加 DP 或 梯度累积步数。
    • 对于长序列，也可以扩展 CP。
  • 若当前批次过大：
    • 缩减 DP。
    • 对于长序列，可减少 CP 以降低显存使用。

步骤 3：优化训练吞吐量

当模型能正常训练且批次大小合理后，接下来要提升训练速度。

  • 优先扩大 TP（通常在节点内扩展，通信代价低）以减少参数复制。
  • 增加 ZeRO-3 数据并行规模，直到通信开销成为瓶颈。
  • 一旦 DP 的通信成为瓶颈，考虑引入 PP。
  • 尝试不同的微批次大小（MBS），寻找计算、通信与内存占用之间的最优平衡点。
  • 尽可能在节点内使用高速互联（如 NVLink）调度 TP 或 PP，以最大化带宽利用。
